# Client UI Kit

## Purpose and responsibility

Reusable, styled, accessible building blocks: buttons, cards, dialogs, tables, and so on. They contain no application logic and know nothing about chat, approvals, or auth.

## Where it sits

The bottom of the client. Every page and feature component imports from it. See [Architecture 2.2](../03-ARCHITECTURE-AND-LIFECYCLE.md#22-client).

## What it is

The files in [client/src/components/ui/](../../client/src/components/ui/) were **generated by the shadcn CLI** and committed to the repo. shadcn/ui is not a package you import; it copies component source into your project so you own and can edit it. [client/components.json](../../client/components.json) records the generator settings: style `base-nova`, base colour `neutral`, CSS variables on, lucide icons.

This project's variant is built on **Base UI** (`@base-ui/react`) for behaviour (focus management, keyboard handling, portals, ARIA) rather than Radix, which older shadcn setups use.

You rarely need to read these files. Treat them like a vendored library.

## Patterns you will see in every file

### `cn()`

```ts
export function cn(...inputs) { return twMerge(clsx(inputs)) }
```

([utils.ts:4-6](../../client/src/lib/utils.ts#L4-L6)). `clsx` joins class names and drops falsy values, which makes conditional classes easy: `cn("flex", isUser && "flex-row-reverse")`. `twMerge` then resolves conflicts between Tailwind classes so the last one wins: `cn("px-2", "px-4")` gives `px-4`. Together they let a caller override a component's default styles through `className`.

### `cva` variants

`class-variance-authority` maps props to class strings. `buttonVariants` declares a base string, then options for `variant` (`default`, `outline`, `secondary`, `ghost`, `destructive`, `link`) and `size` (`default`, `xs`, `sm`, `lg`, and four icon sizes) ([button.tsx:5-40](../../client/src/components/ui/button.tsx#L5-L40)). `<Button variant="ghost" size="icon">` selects from those tables.

`buttonVariants` is exported separately so non-button elements can look like buttons. `AppLayout` uses it to style router `NavLink`s ([app-layout.tsx:20-25](../../client/src/components/app-layout.tsx#L20-L25)).

### `data-slot`

Every component sets a `data-slot="..."` attribute. Parent components style children by slot with selectors such as `has-data-[slot=alert-action]`, instead of relying on DOM structure.

### The `render` prop

Base UI triggers accept `render={<Button ... />}` to say "render as this element and merge my behaviour into it". You will see it on every `DropdownMenuTrigger` in the app, for example [theme-toggle.tsx:23-27](../../client/src/components/theme-toggle.tsx#L23-L27). It avoids a button nested inside a button.

## Theming

[index.css](../../client/src/index.css) does four things:

1. Imports Tailwind v4, animation utilities, shadcn's base styles, and the Geist variable font (lines 1-4).
2. Declares a `dark` variant that applies whenever an ancestor has the `dark` class: `@custom-variant dark (&:is(.dark *))` (line 6).
3. Maps Tailwind colour names to CSS variables inside `@theme inline`, so `bg-primary` means `var(--primary)`.
4. Defines the variables twice: under `:root` for light and under `.dark` for dark.

Switching theme is therefore just toggling one class on `<html>`, which the [App Shell](client-app-shell.md#theme-no-flash-on-load) does. No component has theme-specific logic.

Tailwind v4 is configured in CSS and through the Vite plugin. There is no `tailwind.config.js`.

## The one file with app coupling

`sonner.tsx` imports the app's own `useTheme` so toasts match the chosen theme ([sonner.tsx:1-10](../../client/src/components/ui/sonner.tsx#L1-L10)). It passes `theme` (which may be `"system"`), and sonner resolves `system` itself.

## Lint exception

Files here export both components and helpers such as `buttonVariants`, which the `react-refresh/only-export-components` rule would flag. The rule is switched off for this folder only ([eslint.config.js](../../client/eslint.config.js)).

## Inputs, outputs, side effects, dependencies

- **Inputs:** props and `className`.
- **Outputs:** DOM.
- **Side effects:** none beyond what Base UI does (portals, focus trapping).
- **Depends on:** `@base-ui/react`, `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react`, `sonner`.

## Why it is built this way, and trade-offs

- **Owning the source** means any component can be changed freely, and there is no library upgrade to break things. It also means upgrades are manual: re-run the generator and merge.
- **Long class strings** are the price of Tailwind plus generated code. They are noisy to read but you seldom need to.
- **Two unused components** are harmless dead weight; the bundler drops them.
